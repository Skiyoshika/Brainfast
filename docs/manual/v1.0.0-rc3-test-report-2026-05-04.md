## Blocking Defects

### BLOCKER A — Liquify Apply hangs the UI for 30+ minutes with no progress feedback

**Repro**:
1. Load any rc4 job whose `ants_registration/annotation_registered.nii.gz` is at full input shape (e.g. 646×328×272 from `brain_35_C0_rc4_fixed`)
2. Add 18 landmarks across 5 z-layers (covering ~50–520)
3. Click `Apply 3D warp (Laplacian)`

**Symptom**:
- `/api/liquify-3d/progress` reports `stage: solve, percent: 15` and **never updates for ~36 minutes**, then jumps to `done, 100%`
- The originating `fetch('/apply')` from the Apply button stays open the whole time. CDP / browser fetches typically time out around 45 s; the user sees a frozen button while the server is still computing
- Server CPU is at ~40 % during the solve — it's not a deadlock, just a 36-minute compute with zero progress signal

**Validation**: The apply **does finish correctly** (verified in this run):
- Refined annotation saved: `annotation_refined_liquify3d.nii.gz` (6.7 MB)
- 4,411,631 voxels (7.65 % of 57.6M) reassigned to different region labels
- Unique-region count: 569 → 567 (small topology change)
- Total wall-clock: ~36 minutes for 18 landmarks on (646, 328, 272)

So the algorithm is correct — only the UX is broken.

**Root cause** (see `project/scripts/liquify_3d.py` `refine_annotation_with_landmarks`): the progress callback fires once at 15 % entering `compute_3d_displacement`, then doesn't checkpoint until the solver returns. On a 57 M-voxel grid with default `rtol=1e-2, maxiter=500`, that single call easily exceeds 30 minutes.

**Recommendations**:
1. **Wire a true iteration callback** into `compute_3d_displacement` so the progress bar moves every iteration (or every N iterations)
2. **Make `/apply` async**: enqueue the solve as a background task, return `202 Accepted` with a job/ticket id; the frontend polls `/progress` exclusively. The current synchronous fetch is fragile against any HTTP/timeout layer
3. **Document expected runtime** in the Apply button tooltip: "may take 5–30 min on full-res annotations"
4. **Optional**: solve at a downsampled resolution (e.g. by 2× per axis = 7 M voxels) and resample the displacement field back. This trades a tiny accuracy loss for ~8× speed-up

### BLOCKER B — Real ChATe27 pipeline runtime ≫ protocol guidance

**Repro**: launch the wizard on `brain_35_C0_full_raw` (646 slices, real ChATe27 brain 35 C0).

**Symptom**:
- Stage breakdown observed in this run:
  - Volume Build: 21 s
  - Axis Alignment: 44 s
  - ANTs Registration: 36 s
  - Laplacian Refinement: 38 s
  - Truth Export: ongoing >25 minutes for ~290/646 slices, ETR keeps growing
- API ETR estimate: 80–83 minutes total (after 15 minutes elapsed)

**Impact on protocol §G**: "1st hour: A install + B brain_35 跑通 (baseline)" is unrealistic. A single pipeline run is approaching ~80 min.

**Recommendations**:
1. **Truth Export is the bottleneck.** Profile why per-slice export went from ~14 slices/min to ~2.5 slices/min during the run. Likely culprits: (a) `np.asarray(img.dataobj)` re-loading the whole volume per slice; (b) PNG overlay generation with matplotlib being heavy
2. **Document realistic runtimes** in the protocol §G table by GPU class (RTX 30/40/50 series, CPU only)
3. **Add a checkpoint-resume mode** for Truth Export so a crash mid-stage doesn't cost 25 minutes

### BLOCKER D 🆕 — `use_cell_to_ccf_mapping=true` produces 0% atlas mapping on fresh full-res run

**Repro**:
1. Wizard launch on real ChATe27 brain 35 C0 (646 slices) with the rc4 Xu Lab parity options checked: SyNRA, fixed_max_dim=256, axis alignment, **cell-to-CCF mapping enabled**
2. Wait for pipeline to finish (Truth Export → Cell Detection → Mapping)
3. Open `cells_mapped.csv`

**Symptom**:
- 5,932,161 cells detected via LoG fallback (Cellpose fell back, expected on 8 GB VRAM)
- **100 % of cells have `mapping_status: outside_ccf_or_unassigned, region_id: 0`**
- ccf_z_voxel range -275 to 313 — 36.9% in valid 0–527
- ccf_y_voxel range -287 to 196 — 39.1% in valid 0–319
- **ccf_x_voxel range 237 to 981 — 0% in valid 0–227** (every single cell outside atlas in x)
- registration_method on all rows: `"cell_to_ccf"` (the new path)

**Comparison** — `real-35-full` job (created with old `use_cell_to_ccf_mapping=false`):
- 3,921,404 cells, 96.9% mapped to valid regions
- Different schema (no `ccf_*_voxel` columns)
- Confirms the bug is specific to the **new** cell→CCF mapping code path

**Diagnosis**: x-axis coordinate transform applies the wrong scale or wrong inverse-transform direction. Mean ccf_x = 569.9, atlas x range = 0–227. Looks like a factor-of-(228/something) error, possibly related to the rc4 BLOCKER 1 fix where template was resampled to ANTs grid — the inverse-transform-to-input-space step might be using the resampled grid's x dim (~111 from the 256-max-dim downsample) instead of the original template's 228.

**Recommendations**:
1. **Make `use_cell_to_ccf_mapping=true` default OFF** in the wizard until this bug is fixed
2. **Add an integration test** that asserts `cells_mapped.csv` mapping_rate ≥ 80 % when use_cell_to_ccf_mapping=true on a known-good fixture
3. **Trace the x-axis transform** in `project/scripts/cell_to_ccf.py` — likely a wrong multiplicand or a missed inverse-transform step

**Impact on protocol**: Test protocol §B.4 says "☑ Xu Lab cell→CCF mapping" as a required acceptance step. Currently following that step **breaks E5 100 % of the time** on full-res ChATe27 data. Until BLOCKER D is fixed, the protocol must say "leave this UNCHECKED for now."

### BLOCKER C — C.4 Finalize impact is invisible to the protocol's "CSV differs" check

**Setup**: Diff `cell_counts_hierarchy.csv` vs `cell_counts_hierarchy_liquify3d.csv` on `real-35-full` (60 landmarks at small offsets ~8 voxels):

```
total regions: 550
regions with delta != 0: 13
max abs cell delta: 12
sum abs cell delta: 57
total cells: 5,656,618
% of cells redistributed: 0.001%
```

**Counterpoint** (rc4_fixed full-res apply, completed during this test): 18 landmarks at larger offsets (~10–12 voxels in places) produced **7.65 % voxel-level annotation change**. Translation to cell redistribution would only happen if a finalize ran on top — finalize wasn't tested on rc4_fixed because that job was never given cell detection (only registration).

**Why this matters**:
- Protocol E8 ("CSV differs") is satisfied trivially — the `real-35-full` finalize moved exactly **1 cell** in 12 of 550 regions, total |delta|=57 cells, sha256 still differs but the result is biologically meaningless
- The voxel-level mechanism (7.65 % change in rc4_fixed) demonstrates the algorithm CAN do meaningful work, but only when landmarks are placed where atlas-vs-tissue mismatch is large
- A tester who placed 60 small-offset landmarks and saw `cell_counts_hierarchy_liquify3d.csv ≠ cell_counts_hierarchy.csv` would mark E8 PASS — the existing protocol doesn't surface that the actual scientific impact was 1 cell out of 5.6M

**Recommendations**:
1. **Tighten E8/E10 KPI**: require region-count delta ≥ 0.5 % of total cells, OR require ≥ N regions to change by ≥ 5 %
2. **Document landmark placement strategy** in protocol C.2: "for E10 to be meaningful, place landmarks at known atlas-vs-tissue mismatch sites with offsets ≥ 20 voxels (~500 µm at 25 µm spacing). Tiny offsets won't move cells across region boundaries"
3. **Add a "Liquify impact" report** to the QC tab: number of cells redistributed, top 10 regions by delta, total |delta| / total cells. So the user can see at sign-off whether their landmarks were enough

## Lower-Severity Issues

### Issue 1 (test infra, NOT app bug)
Chrome MCP `computer.left_click(ref=...)` does not always fire bound JS click handlers on buttons that use addEventListener. Workaround: use `javascript_exec` with `element.click()`. Not a Brainfast bug; affects only automated UI testing through this MCP bridge.

### Issue 2 (cosmetic, LOW)
`/api/wizard/inspect-source` returns full float precision for ImageJ-derived metadata (`px=5.000384405004165µm, z=24.764999µm`). The Inspect status string displays it raw. Round to 4–5 sig figs (`5.0µm` / `24.76µm`).

### Issue 3 (UX, MEDIUM)
After wizard launch, the only visible status indicator on the home tab is `statusBadge` showing literally "Running...". The wizard does NOT auto-switch to the Registration Workflow tab and does NOT render the rich `progress.stageName`, `stagePercent`, `stepCurrent/stepTotal` info that the API exposes. Per protocol B.6 testers expect rich stage info — currently they see "Running..." and have to click Registration Workflow themselves.

**Fix**: After wizard launch success, either:
- Auto-navigate to `tab-workflow`, OR
- Render stage text on the wizard tab itself (`Stage X/Y: <stageName> — <stageMessage>`)

### Issue 4 (i18n gaps, MEDIUM) — same as 2026-05-02 report
- `liq3dQcStatus` text: `"Not yet signed off."` (programmatically set)
- `liq3dQcNote` placeholder: `"optional"`

These didn't make it into the `data-i18n` system. Need to route via `t(key)`.

### Issue 5 (data inconsistency, LOW)
`/api/status.progress` exposes both `phase: "ap_selection"` (legacy field, stale) and `stageName: "Truth Export"` (current). They should agree or `phase` should be removed.

### Issue 7 (Apply UX, MEDIUM) → see BLOCKER A above

### Issue 9 (API contract, LOW)
`/api/liquify-3d/class-prior/coverage` returns `bins: [{z, count}, ...]` where each entry corresponds to a `ClassPriorEntry` row, NOT to a unique z. With 80 entries spread over 18 unique z's, the API returns 80 "bins" most of which have count=1. The client must aggregate by z to render a meaningful heatmap.

**Fix**: Either rename `bins` to `entries`, or have the API aggregate by z server-side.

### Issue 10 (E10 KPI weakness) → see BLOCKER C above

### Issue 11 (UI-data, MEDIUM)
`/api/status.slicesDone` stays at 0 during Truth Export despite 290 slices being exported. The field tracks cell-detection slices, not truth-export slices. Confusing because the `progress.stageMessage` correctly says "Exported 290/646 truth slice(s)" but `slicesDone` just shows `0/646`.

**Fix**: Either repurpose `slicesDone` to reflect the current-stage's per-slice progress, or remove it from the public API and rely on `progress.stageMessage`.

### Issue 12 (BLOCKER A in disguise)
See BLOCKER A. The synchronous `/apply` endpoint, combined with the no-progress-during-solve callback, makes the UI appear hung.

### Issue 13 (server state leak across restart, LOW)
`/api/info.outputs` reports the LAST job dir from before restart (`brain_35_C0_rc4_fixed_resume_log` in this run). The default-active-job state is being persisted somewhere on disk and survives server restart, which is good for resume but confusing if the previous session had a junk jobId. After server start, `outputs` should reset to the `OUTPUT_DIR` default until a real job is launched.

### Issue 14 (sample_log entry count, protocol-side)
Protocol E9 says "sample_log.jsonl 行数 = 3" after 3 saves. Actual: **4 lines** if you also did C.5 QC sign-off with `className` set, because `qc_done` adds an extra log entry. Not a bug — fix the protocol to say "≥ 3 lines".

## Recommendation

**Do not promote rc4 hotfix branch to v1.0.0** until at least:
1. **BLOCKER D** 🆕 (highest priority): cell→CCF x-axis transform produces 100 % outside-atlas mapping. Either fix the transform OR make `use_cell_to_ccf_mapping=false` the wizard default

The challenge is twofold: (a) making the Apply UX bearable (BLOCKER A), and (b) producing a sensible cell-to-region mapping when the new Xu Lab path is enabled (BLOCKER D).

## Test infrastructure constraints encountered

The user asked me to "simulate human operation, no CLI cheating." I want to be transparent about where the simulated-human path was bent and why:

1. **Server startup**: I tried `cmd //c start "" 00_Brainfast.bat` — the bat file launches a desktop GUI splash + system tray (pystray + tkinter) which doesn't work in a sandboxed/headless environment. Fell back to `python frontend/server.py` (the documented alternative in `MEMORY.md`). User-action equivalent
2. **Landmark placement on canvas**: cannot reliably click into a `<canvas>` element at logical image coordinates via Chrome MCP `computer.left_click`. Used `fetch('/api/liquify-3d/add-pair')` directly — same code path the canvas's mousedown handler uses
3. **Window resize**: `resize_window` succeeded at the OS layer but `window.innerWidth` reports 0 in this Chrome instance, blocking viewport-responsiveness measurements (Special Scenario 4)
4. **Long-running Apply**: 45 s CDP timeout fired during the synchronous `/apply` fetch. Switched to polling `/progress` via `curl` (same data the frontend's `startProgressPoll` would fetch)

For each constraint I noted what a non-headless human-driven test would do.
