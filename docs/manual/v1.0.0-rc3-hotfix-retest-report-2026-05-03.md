## New / Remaining Issues

### BLOCKER 1: Default Laplacian parallel workers crash on Windows

Normal UI-launched job: `brain_35_C0_rc4_retest`

The job failed in Laplacian correspondence extraction:

```text
joblib.externals.loky.process_executor.TerminatedWorkerError:
A worker process managed by the executor was unexpectedly terminated.
This could be caused by a segmentation fault while calling the function
or by an excessive memory usage causing the Operating System to kill the worker.
```

Root-cause evidence:

- Failure happens in `project\scripts\regtools_laplacian\correspondence.py` at `Parallel(n_jobs=-2)`.
- Same inputs succeeded when replayed with `LOKY_MAX_CPU_COUNT=2`, which makes `n_jobs=-2` effectively single-worker.
- Probe output succeeded in 37.9 s and wrote `final_registered.nii.gz`, `laplacian_deformation_field.npy`, and `refinement_metrics.csv`.

User impact: a normal scientist using the one-click launcher has no obvious way to cap joblib worker count, so B fails before cell detection/count export.

### BLOCKER 2: `fixed_max_dim=256` still leaves annotation on the wrong grid

Continuation job with limited concurrency: `brain_35_C0_rc4_loky2`

After the Laplacian solve completed, the pipeline failed here:

```text
ValueError: refinement field shape (256, 155, 111)
does not match annotation volume (528, 320, 228)
```

Shape evidence:

```text
ants_result.nii.gz                         (256, 155, 111)
template_resampled_for_laplacian.nii.gz    (256, 155, 111)
laplacian_deformation_field.npy            (3, 256, 155, 111)
original annotation volume                 (528, 320, 228)
```

Likely root cause: `whole_brain_3d.py` now resamples the template for Laplacian, but `_apply_refinement_field_to_annotation_volume()` is still called with the original `template_meta["annotation_path"]`. The annotation needs to be resampled to the same ANTs/Laplacian grid before applying the field, or the field needs to be transformed back to annotation grid.

User impact: even after capping concurrency, the full B pipeline still cannot reach truth export, `cells_mapped.csv`, or count CSVs when `fixed_max_dim=256` is used as required by the protocol.

### HIGH 3: Error visibility is still fragile outside the active frontend session

Job-scoped API error retrieval works:

```text
/api/error-log?job=brain_35_C0_rc4_loky2
=> channel red failed with code 1
```

However, after restarting the app and launching a job through API for continuation, the browser Error Panel showed `当前没有记录到错误。` while the job-specific error endpoint had the failure. This may be expected because the continuation launch bypassed frontend active-job state, but from a user-support perspective errors remain too easy to hide unless the active job is explicitly bound.

## Overall Conclusion

Not ready for v1.0.0 acceptance.

The previously reported UI issues around quoted paths, multi-page TIFF wording, and wizard launch visibility are materially improved. The key rc4 `fixed_max_dim=256` shape fix is only partial: template and ANTs grids now match, but the pipeline still fails first under default joblib concurrency and then, after concurrency is limited, fails because the annotation volume remains on the original grid.

Recommended next development targets:

1. Add a safe default or config option for Laplacian correspondence `n_jobs` on Windows instead of hard-coding `Parallel(n_jobs=-2)`.
2. Resample annotation to the same grid as `ants_result.nii.gz` / `template_resampled_for_laplacian.nii.gz` before applying the Laplacian field, or resample the field back to the annotation grid.
3. Keep the job ID visible and bound in the Errors panel across reloads/restarts, or provide a user-facing job selector for recent failed jobs.
